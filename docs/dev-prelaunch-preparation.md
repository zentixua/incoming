# Prelaunch ruin preparation

`nuclear.world.RuinPreparation` is a server-thread facade over the existing world preparation owner. A handle has an owner UUID, a dimension, target, yield and burst mode. It is independent of flight duration. UI and commands must validate permissions and identity before calling it; these Java methods are not a client authorization boundary.

`prepare` opens or renews a compatible handle. Only one unlaunched handle per owner exists across dimensions. The server-wide limit is eight live or draining handle requests; the existing shared preparation byte admission budget still applies. Refused admission returns ABSENT through `status`; no unbounded rejection ledger is retained. `status` returns immutable Stage, ready/total chunk counts, required read/solver/write counts, resident estimate, Reason and nullable authoritative resolvedTarget. It does not walk the zone. The initial total is unknown until the asynchronous layout arrives.

The 1200-tick inactivity lease is renewed by `keepAlive(level, handle, owner)` after server identity/order validation. A watched fifteen-minute preparation can renew indefinitely. Accepted paid orders awaiting a second key or carrier warning must renew from their server tick even after the UI closes. `bind` requires READY and an already scheduled order matching the exact owner, resolved target, yield and burst mode. It transfers to the actual strike ID and disables inactivity expiry. Cancellation of an unlaunched owner works across dimensions; explicit handle cancellation also releases bound preparation without cancelling the scheduled strike itself.

READY requires every heavy-zone center to have a plan or an explicit absent/partial source result, no required disk reads or solver tasks, and no required pending plan/snapshot writes. Ordinary resident snapshots are reconstructible cache; admitted snapshot writes must finish, and all prepared plans must reach the page writer. Failed or pending receipts cannot certify readiness. This is normal clean-save durability, not a promise of atomic survival across region files under power loss. Resource generation and geometry-affecting settings invalidate readiness. Application still validates source blocks through the existing store/ruin path.

Surface resolution uses authoritative ready terrain or the asynchronous disk terrain survey, never the client target Y. Unknown terrain remains RESOLVING. A request with no generated disk terrain can remain unresolved until that terrain exists. On reconnect/restart a new request revalidates and rebuilds; no readiness certificate is persisted. UUID archive paths survive binding and are assigned to the actual `RuinProgress` event at handoff. The legacy numeric archive path remains readable.

The scheduling caller must carry the explicit handle to `bind`. The detonation caller must forward the actual scheduled strike ID through `NuclearWorld.planned(fresh, strikeId)` and `onDetonation(level, detonation, owner, strikeId)`. Existing overloads exclude handle preparations, so immediate diagnostics cannot steal a preparation by proximity. The legacy scheduled-flight preparation path remains available without a handle.

Lifecycle GameTests cover ownership, cross-dimension cancellation/admission, lease renewal/expiry, write gating, exact binding and terrain resolution. Small fixtures do not establish the full 1 Mt preparation target of 10–15 minutes or a total heap bound; those remain integration measurements.
