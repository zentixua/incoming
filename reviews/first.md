## B1 — P2: scanner and decoder disagree on accepted section-header types

**Locations:** `mod/src/main/java/ua/zentix/incoming/nuclear/world/LedgerScan.java:178-183` and `:80`; `RuinOriginals.java:219-225`. Downstream admission/publication: `LedgerLoads.java:92-110` and `:74-80`.

`LedgerScan` recognizes `original_entries` only when the NBT tag ID is 3 (`IntTag`). Any other numeric type is skipped as ordinary payload, leaving `originalEntries == -1`; the `original_sections` row then contributes **zero section ownership**. `RuinOriginals.read`, however, tests only key presence and calls `CompoundTag.getInt`, which accepts all numeric tag types. A `LongTag(4096)` or `ShortTag(4096)` therefore preallocates the complete section and is accepted when its 4,096 unique cells arrive.

I checked the local Minecraft/NeoForge source for this API behavior: `CompoundTag.java:317-329,355-363` in `~/.gradle/caches/neoformruntime/intermediate_results/sourcesWithNeoForge_8d8dd8d3471ede4eff13ebf581fab2d1d8e43bf2_output.zip`. `getInt` explicitly uses numeric type 99; this is not an assumption about a cast.

**Causal example:** take an otherwise valid current-format file containing one full section in 64 bounded rows; encode only its first `original_entries` as a long with the same value 4096. All positions, named states, events and counts remain valid. The scanner omits the section's roughly 98 KiB backing allowance, while the reader allocates it and completes successfully. Repeating distinct complete sections scales the discrepancy without increasing the largest row. `LedgerLoads` reserves only the scan result and publishes the restored ledger without a post-read ownership ceiling, so sufficiently many such sections can bypass the 512 MiB ownership gate altogether. Even a truncated version allocates the uncharged page before the final completeness rejection.

**Required correction:** align the accepted schema at the allocation boundary. The simplest option is to reject an existing `original_entries` whose type is not exactly `TAG_INT`, before constructing `Page`; alternatively, make the scanner account for every numeric representation the decoder accepts. Preserve the source file on rejection.

**Smallest discriminator for MT-S7:** extend `nuke_original_bounds` with a header made by `putLong("original_entries", 4096)` (and a short variant). Require rejection before page allocation, or identical funded measurement if intentionally supporting it. A one-section, 64-row `LedgerScan`/`LedgerReader` file test should require either rejection or `restored.retainedBytes() <= measured.owned()`. No large/world/game reproduction is needed to distinguish this.

**Confidence:** confirmed by source, including the actual NBT accessor; the discriminator was not executed by this reviewer. This is an error-path/admission defect. The current writer uses `putInt` at `RuinOriginals.java:206`, so ordinary self-generated saves do not trigger this condition.

## C1 — nonblocking: the isolated growth estimate/test does not prove intermediate rehash peaks

`RuinOriginals.Table.growth` (`:26-29`) returns only the final new table size. For an already materialized page that grows through multiple capacities in one batch, the last rehash overlaps an intermediate table, not the small table counted at admission. For example, start with two entries (`n=4`) and add 3,071 unique cells in that same section: the last transition is `4096 -> 8192`, whereas the formula adds only `tableBytes(8192)` over the original `n=4` owner. New/singleton pages already use a double-table allowance; existing non-singleton pages do not. The outer `Pages.growth` has the analogous multi-growth shape for small indexes.

This falsifies the helper's standalone “complete ... including rehash scratch” wording. It is **not** a demonstrated 512 MiB production violation: `RuinMatter.removalBytes` also reserves conservative capture/index/support ownership, and the ledger has fixed I/O workspace. I did not prove those aggregate allowances are exhausted at this peak. Do not report this as a reproduced heap overflow.

The new dense test (`RuinOriginalsGameTests.java:38-43`) adds a separate fresh chunk and compares the final `bytes()` with the final allowance. It cannot catch this intermediate-capacity case. A small existing-page growth discriminator, or direct pre-sizing to the funded capacity, would close that narrower proof gap. No extra broad benchmark is requested.
