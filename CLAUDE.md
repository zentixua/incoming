# Incoming — мод NeoForge для Minecraft 1.21.1 (сборка «Open Skies»)

Id и пространство имён — `incoming`, команда `/incoming`, пакеты `ua.zentix.incoming`, jar `incoming-<версия>.jar`,
настройки `incoming-server.toml`/`incoming-client.toml`. Старые миры с id `airstrike:*` открываются через `legacy/`
(`OldNamespace` — псевдонимы реестров и файлов `data/airstrike_*.dat`, `LegacyMigration` — переезд со старого датапака).
Сборка «Open Skies» — личная, Артёма с друзьями: в публичных текстах мода её нет.

Кинематографичные и при этом реалистичные удары: Shahed-136, «Ланцет», «Град», крылатая ракета, B-2 с бетонобойной
бомбой, залпы, МБР с ядерной боевой частью; пульт наведения с биноклем, наведение на всё, куда смотрит игрок (блоки,
мобы, игроки, аппараты Create Aeronautics), свой 3D-звук с Доплером. Репозиторий публичный:
https://github.com/zentixua/incoming. Всё это — внутри игры: снаряды, пусковые, ПВО, цели, города и «игроки» — блоки, сущности
и персонажи Minecraft. Играют Артём и друзья: в одиночной игре, в мире хоста, открытом друзьям, и на выделенном сервере
(белый список, оператор — только хост).
Руководство игрока — docs/guide (README.md — обзор и установка): изменение, заметное игроку, правит и руководство в том
же PR, на обоих языках (docs/guide — английский, docs/guide/ru — русский), кадры — `tools/client_scenario.sh guide` и
`tools/guide_images.sh`. Проект ядерного удара и отступления от него — docs/DESIGN-nuke.md.
Рядом — свои репозитории со своим CLAUDE.md: сборка «Open Skies» (zentixua/open-skies) и Almighty, мост ИИ-ведущего
(zentixua/almighty).

Здесь — только то, что нужно в каждой сессии. Устройство пакетов и подводные камни по областям — в `.claude/rules/`
(список в конце): файл области подгружается сам, когда Claude открывает её файлы инструментами Read, Edit или Write.
Читаешь код через Bash или планируешь работу, ещё не открыв файлов, — прочитай файл правил области сам. Новое правило
или камень — в файл своей области; сюда — только общее для всех сессий.

## Люди и правила общения
- Автор/хост: **Артём**, в игре **ZentixUA**. Друзья: **ENOTzRPG**, **WallyFillmark**.
- Общаемся по-русски, кратко и по делу.
- Публичные тексты — по-английски: README.md, руководство, описание мода, страницы магазинов (docs/store), заметки
  к релизам, ключи en_us; русский перевод (README.ru.md, docs/guide/ru, ru_ru) правится в том же PR. Пишем как человек:
  просто, точно, без рекламных слов, повторов и воды; каждое утверждение сверено с кодом.
- **Не управлять компьютером пользователя** (никакого computer-use, кликов в игре). Всё готовим так,
  чтобы Артёму оставалось только запустить игру: мод приходит в неё выпуском и PR сборки в open-skies (автообновление).
- **Минимум просьб «проверь в игре»** — это мешает игре. Проверяем сами: юнит-тесты, GameTest, клиент без окна
  (`tools/client_scenario.sh`), после игры — `tools/logscan.py`.
- Не удалять миры/сейвы/файлы пользователя. Лишнее — переносить в сторону (`deploy.sh` кладёт в `incoming-backup/`).
- Качество важнее скорости: перед сдачей — сборка, тесты, GameTest, ревью диффа.
- **Доводить до конца без вопросов**: когда работа готова и проверена (сборка, тесты, GameTest), самому влить свой PR
  (после зелёного CI, чистого независимого ревью и вердикта координатора) и довести мод до игры: `tools/deploy.sh` —
  в инстанс без автообновления сборки, в инстанс с ним мод приходит выпуском и PR сборки. Артём должен застать мод
  готовым к игре, а не список шагов для себя. Спрашивать только то, что меняет цель или чего нельзя отменить.
- Публичные шаги (релиз на GitHub, Modrinth, YouTube) — только по прямому слову Артёма.

## Где что лежит

## Рабочий цикл
```sh
export JAVA_HOME=~/.var/app/org.prismlauncher.PrismLauncher/data/PrismLauncher/java/java-runtime-delta
cd mod && ./gradlew --daemon build        # компиляция (-Xlint:all без предупреждений) и юнит-тесты; --daemon — тёплый
                                          # демон: правка → компиляция 16 → 4 с; только build/test/compile — запуски игры
                                          # (run*) и скрипты без него; `gradlew --stop` не звать: гасит демоны всех сессий
cd mod && ./gradlew runGameTestServer     # GameTest: сервер без окна с Create 6.0.10, Sable 2.0.6, Aeronautics 1.3.2
cd mod && ./gradlew runScenarioSweep      # одни сценарии полёта, все зёрна (-PscenarioSeeds=N, по умолчанию 16;
                                          # -PscenarioOnly=<регвыр> — выбор, -PscenarioRealChunks — настоящая загрузка)
cd mod && ./gradlew runScenarioRecord     # записать эталон траекторий заново (сдвиг — объяснить в PR по сценариям)
tools/client_scenario.sh nuke             # клиент без окна: mod/run/scenario/screenshots/*.png, audio.wav, logs
tools/sandbox.sh shot <имя> '<эффект>'    # картинка и звук: кадры и WAV одного эффекта за ~10 с после правки, без нового
                                          # клиента (start — один раз); рядом с эталоном выпуска — проверка PR; полная
                                          # сборка под Iris — раз на кандидата выпуска (client-scenario.md)
tools/deploy.sh                           # jar → dist/ (для друзей) и mods/ инстанса без автообновления сборки
python3 tools/logscan.py [--since 18:30]  # после игры: ошибки мода, удары, подрывы, Sable
```
Скрипты с пакетами (numpy, scipy, soundfile, Pillow) объявляют их сами блоком `# /// script` (PEP 723) — запуск
`uv run tools/<скрипт>.py`, в системный Python ничего не ставить.
Без инстанса (облако, CI): `python3 tools/fetch_runtime_mods.py` → `./gradlew runGameTestServer -PmcModsDir=run/ci-mods`.
CI гоняет проверки один раз на коммит: push в `main` и PR — ветка без PR CI не запускает, поэтому PR открывать сразу,
черновиком; проверяется то, что изменилось (правка только `tools/`, `docs/`, `*.md` мод не собирает — исключения в `tools.md`), релиз — целиком.
Слияние решает задача «Итог»: падает, если упала или отменена любая нужная проверка.
Зелёная проверка «Записка» (`note.yml`) — тоже условие влития, как «Итог»: PR с видимым или слышимым игроку — с `## Записка`.
Релиз — `mod_version`, `docs/releases/<версия>.md`, ручной `build` с `release=true`, PR сборки (порядок — `tools.md`).
Версию протокола (`IncomingNetwork.PROTOCOL`) поднимает PR, который меняет формат пакетов или данных сущностей; релиз,
у которого поведение или ключи языка отличаются от прошлого выданного jar, поднимает её сам, если за выпуск её ещё
не подняли: старый jar не должен заходить к новому хосту (NeoForge тогда говорит «разные версии мода»).

## Архитектура (пакеты `ua.zentix.incoming`)
Пакеты названы по областям (`strike/` приказы и пуск, `entity/` и `guidance/` полёт, `warhead/` взрыв, `nuclear/`,
`defense/` ПВО, `launcher/`, `grid/` блэкаут, `sound/`, `client/`, `work/` бюджет тика); устройство — в файлах правил.
Правила, общие для всех пакетов:
- **Паспорт оружия** `WeaponSpec` (`WeaponType.spec()`): число, которым оружие отличается, — в паспорт.
- `net/ClientHooks` — интерфейс, который реализует клиент: сервер не грузит клиентские классы.
- `compat/SubLevels` — вся связь с Sable. Миксины — в `mixin/<мод или область>/`.
- `util/Terrain` — готовность чанка и «где земля»: высота земли — только через него, прямых
  `getBaseHeight`/`getSeaLevel` вне него нет (`server-chunks.md`).
- Состояние сервера, которое не сохраняется, — несохраняемые attachments NeoForge (мира или игрока), а не статические
  карты: статика переживает смену мира в одиночной игре.
- `sound/` — звук снаряда без Minecraft, общий для сервера и клиента (источник, распространение по ISO 9613, спектры
  записей от `tools/build_sounds.py`); докуда слышно — `strike/Hearing`.
- Команда `/incoming` (`command/IncomingCommand`): новая команда или синтаксис — и в памятку ИИ-агенту Almighty
  `data/incoming/almighty/notes/strikes.md`. Рецепты боеприпасов — с Create и ванильной заменой по `neoforge:mod_loaded`.

## Принципы: физика и настройки
Мод — самый физически верный в своей нише, и поэтому красивый. Это правило для каждой правки:
- **Пуск — игровой, у цели — по физике.** Скрафтил, нажал «пуск»; у цели — заряд, взрыв, осколки, разрушения, урон —
  и картинка со звуком — по ТТХ настоящего изделия и законам. Каждое число — из паспорта (`WeaponSpec`) или закона,
  источник рядом; где данных нет — оценка с отметкой; где закон приближённый — сказано.
- **Полёт и ПВО — своя игровая модель** (решение Артёма 21.10): правдоподобная и серьёзная, но не повтор настоящих
  изделий 1:1 — ни их ТТХ полёта, ни их наведения, радаров и моделей поражения. Законы одни на класс (инерция и крен
  разворота, обмен высоты на скорость, тяжесть, сопротивление и ветер у неуправляемых — `guidance/`), числа — в
  паспорте (`WeaponSpec.Handling`, `Ballistic`), игровые и помечены «не по физике».
- **Причина, а не следствие.** Неверный результат чинится в модели, которая его даёт, а не подгонкой результата;
  один закон на класс; число, которым оружие отличается, — в паспорт, не константой и не `switch` по оружию.
  Картинка и звук выходят из модели: кадр не подгоняется.
- **Настраивается причина, а не следствие.** Игрок задаёт условия, мир считает остальное по законам. Настройка —
  одного из четырёх видов: правило мира (какие явления есть, кто что может, залп, время полёта, выбор, который есть у
  настоящего изделия, — мощность ядерки 1–15 кт, высота подрыва); масштаб времени и расстояний под карту (пресет
  `GAME` по умолчанию, `REAL`, `CUSTOM`); производительность (один бюджет работы за тик, качество); удобство игрока.
  Следствий в настройках нет: размер воронки, разрушения, вероятность поражения, пробитие, дальность слышимости, вид
  дыма считают законы. Признак лишней настройки — она названа по следствию («сила взрыва ×», «вероятность
  поражения», «дальность радара») или это множитель без физического смысла.
- **Масштаб под Minecraft.** Блок — метр, поэтому размеры и всё у цели (заряд, осколки, воронка, пробитие, урон) —
  настоящие при любой настройке. Мала в игре дальность видимости и игры (сотни блоков): на настоящей скорости быстрое
  оружие проходит прорисовку за доли секунды. Нужная скорость подлёта — свойство игры, а не изделия, поэтому у каждого
  оружия два числа в паспорте (игровое в `WeaponSpec.Airframe`, настоящее в `Article.Envelope`, с источником) и одна
  шкала мира `scale.flight_speed` (`strike/FlightScale`: 0 — игровые, 1 — настоящие, между — v_игр·(v_наст/v_игр)^x у
  каждого изделия; крейсер, пике, высота маршрута и сброса B-2, скорость зенитной ракеты, сход «Града» и его
  сопротивление; длины из скорости — запас хода, участок, захват точки, геометрия атаки, полоса подлёта — растут с
  маршевой, `Airframe.stretch`; манёвр — игровой). Вывести игровую скорость из прорисовки нельзя: прорисовка у каждого
  игрока своя, полёт — один на сервере. Скорость ядерной волны вдали по умолчанию тоже игровая (0,20 скорости звука).
  Пресет `scale_preset`: `GAME` (по умолчанию) — полёт 0, волна 0,20; `REAL` — всё как в жизни; `CUSTOM` — числа
  `flight_speed`, `nuclear.wave_speed`, `nuclear.effects_scale` как есть.
- **Отступления от физики** — только масштаб из пресета или явное решение Артёма; каждое помечено «не по физике» в
  коде и в списке отступлений руководства (среди них — игровые скорости и высоты полёта и волна 0,20: не настоящие,
  чтобы подлёт и волну было видно; настоящие — в таблице оружия). Тихих отступлений нет.
- **Жалобы не повторяются:** исправленное получает тест или проверку, которые поймали бы его снова.

## Единицы и масштаб
- Блок = метр. Скорости снарядов — блоки/тик, игровые при шкале полёта 0 (`FlightScale`; шахед 2.1, барражирующий
  1.6 и в пике 4, ракета 4 и в пике 5, B-2 12, МБР до 25, зенитная ракета ЗРК до 14; РСЗО и бомба — по баллистике с
  сопротивлением, g = 0.0245 блока/тик²). Звук — 17.15 блока/тик. Воздух мира (ветер, класс устойчивости,
  влажность) — один на полёт, звук и дым: `util/Air`.
- `WeaponType.id` = порядковый номер в перечислении (клиент берёт `values()[id]`): новое оружие — только в конец;
  порядок в пульте и в бинокле — `WeaponType.menu()`.
- Ядерная модель — в метрах, секундах, килотоннах; в блоки и тики её переводит `Detonation` с `effects_scale`, фронт в
  игре — `FrontProfile` (`nuclear.md`). Игровые часы осадков: 1000 тиков = 1 час.

## Как работаем: правильно с первого раза, проверки — в точку
- **Сначала готовое** (Артём 22.10): первый шаг — поиск готовых модов, аддонов и библиотек (Modrinth, CurseForge,
  GitHub, Reddit, витрины; с Fabric — через Roxy и Sinytra Connector). Зависимости мода и сборки приветствуются; своё —
  только то, чего нет ни у кого, с причиной в задании или PR; в предложении таблица «что есть» — раньше «что делаем
  сами». Запрет миксинов в ваниль и чужие моды — про наш код, не довод против чужих модов.
- **Сначала ожидание, потом код** (кроме правки, которую можно описать одной фразой): в задании или описании PR — какой
  закон берём (уже существующий в моде; новый — только когда его нет), где он верен (время, масштаб, земля/воздух/вода/
  ночь) и что игрок увидит и услышит в ключевые моменты (у взрыва — 0,1 / 1 / 10 / 60 с). Формула конечного состояния
  ранние моменты не описывает.
- **Инвариант — тестом**: что выражается числом (пыли без земли нет, ничего не опережает фронт волны, яркость без
  скачков) — юнит-тест; обещание в комментарии или руководстве держит тест, а вид и звук — кадры по записке.
- **Проверяет не автор**: ревью — свежим контекстом по коду против записки (комментарий и текст PR — не доказательство),
  кадры и звук — по моментам записки рядом с эталоном последнего выпуска, один раз. Ревьюер отмечает только то, что
  ломает верность или записку; остальное — необязательно.
- **Картинка и звук — в песочнице, полная сборка — раз на выпуск** (`docs/dev-pipeline.md`): правят и проверяют
  в `tools/sandbox.sh` (кадр в заданный миг за секунды); PR с видимым или слышимым несёт кадры песочницы рядом с
  эталоном выпуска, а эталон снимается один раз на выпуск, а не каждой сессией (хранилище по ключу — п. 6.3 плана).
  Клиент со всей сборкой под Iris (`look_gate`) снимают один раз на кандидата выпуска, все сцены одной задачей против
  прошлого выпуска: `main` до игроков не доходит, сборка берёт только выпуски. Что там хуже — PR-исправление,
  виновного находит `git bisect` кадрами песочницы.
- **Сверх этого проверок нет**: результат с зелёным CI и ревью принят. Ушедшая ошибка закрывается тестом или правилом
  на весь класс, а не новым ручным шагом.
- Разбор нашего процесса (что пошло не так с 01.10, что исправлено инструментами, план) — `docs/dev-process.md`;
  как работают опытные моддеры, наши потери по звеньям и целевые времена конвейера — `docs/dev-pipeline.md`.

## Общие правила кода и проверок
- **Ничего не читать в незагруженных чанках из тика**: `getBlockState`, `clip`, ванильный `explode` и даже
  `TicketController.forceChunk` NeoForge грузят/генерируют чанк сразу — сервер встаёт на 5–6 с. `hasChunk`/`isLoaded`
  верны и для чанка, который ещё грузится, а `getHeight`/`getBlockState` на нём ждут в `managedBlock` (до 400 мс):
  проверять готовность через `getChunkNow` (`util/Terrain`). Для ядерного удара — ванильный `TicketType`
  (`NuclearTickets`, грузит в фоне).
- `Locale.ROOT` для чисел в командах: у Артёма русская локаль, `String.format("%.1f")` даёт запятую.
- Тяжёлые задачи на ноутбуке Артёма — через `tools/laptop_job.sh` (своя служба systemd, не группа приложения Claude:
  общая группа роняет и само приложение). Одновременно — одна задача со всей сборкой (≈12 ГБ) или стенд — очередь
  держит сам скрипт (клиенты и Blender — `--gpu`: ждут и закрытой игры Артёма), лёгкие (`--light`) — рядом, если по
  сумме помещаются в 32 ГБ; прожорливое чинится в коде, а не пределами памяти. `/tmp` там —
  tmpfs в ОЗУ: большие файлы (клоны, копии инстанса, кадры) — на диске, например в `mod/run/` (в .gitignore).
- Ничто из проверок не должно доходить до экрана и колонок Артёма: клиенты — только через `tools/nested_kwin.sh`
  (`--virtual`: окна на рабочем столе нет, звук хоста OpenAL не открывает; звук сценария — в файл), без KWin
  (облако) — `xvfb-run` с тем же закрытым звуком (`rigs.md`).

## Файлы правил `.claude/rules/`
- `tools.md` — раскладка проекта и что умеет каждый скрипт `tools/`, CI.
- `strike.md` (`strike/`, `target/`: приказы, паспорт, пуск, полёт вне мира, районы, итоги попаданий), `entity.md`
  (`entity/`, `guidance/`: полёт, автопилоты, снаряд вне мира, отслеживание сущностей клиентом), `work.md` (бюджет
  тика, массовый урон единицами), `warhead.md` (взрыв по шагам, стёкла, осыпание, частицы ванильного взрыва),
  `defense.md` (ПВО; что можно и нельзя брать целью), `launcher.md` (стационарная пусковая, пуск по редстоуну).
- `nuclear.md` (ядерка без руин: модель, подрыв, радиация, клиент), `nuclear-world.md` (руины, зона за волной, отдача
  чанков игроку), `grid.md` (блэкаут, лампы, свет чанка).
- `server-chunks.md` (чанки, тикеты, выход из мира, сущности, «где земля»), `sable.md` (Sable), `dh.md` (Distant
  Horizons и LOD Server Support: рельеф карты, лучей и звука через их API, LOD вне мира, утечка миров), `voxy.md` (Voxy через Roxy: глубина, изменения мира вдали, LSS).
- `client.md` (устройство клиента, карты высот, Iris и `AFTER_LEVEL`), `client-fx.md` (частицы, слой эффектов,
  шлейф, отсечение альфы), `client-models.md` (модели OBJ), `client-sound.md` (OpenAL, громкость, петли),
  `replay.md` (Flashback).
- `gametest.md` (GameTest и сценарии полёта, без настенных часов), `client-scenario.md` (клиент без окна), `rigs.md`
  (стенд, мультиплеер, вложенный KWin, клиент со всей сборкой), `trailer.md` (трейлер).

## Окружение
- Важные моды: Create 6.0.10, **Create Aeronautics 1.3.2 + Sable 2.0.6** (аппараты — «sub-levels», блоки живут
  в далёком «плоте», их ломает ванильный взрыв через миксин Sable), Sodium, **Iris с шейдерами у хоста**, Distant Horizons,
  Flashback, Essential. Сборка «Open Skies» — 53 мода, рядом инстанс «All of Create Aeronautics» (~217 модов);
  выделенный сервер — сборка с её `main`. jar мода нужен всем — серверу и клиентам.
